# Instruções para agentes (valem para qualquer agente e qualquer modelo)

Projeto: **FrontLine**, jogo de estratégia no navegador (Trincheiras, Trincheiras online e Conquista). Código em `prototipo/` (HTML, JS puro e canvas), testes em `tests/`. Idioma do projeto: **português do Brasil** (issues, PRs, commits, textos do jogo).
Dono do projeto: Douglas (com o parceiro Ruan).

## Fluxo obrigatório: issue → branch → PR → deploy

Toda tarefa é de um destes tipos: **Correção** (bug), **Melhoria** (algo existente fica melhor) ou **Nova função**.

1. **Issue primeiro.** Antes de mexer no código, procure se a tarefa já tem issue; se não tiver, crie uma.
   - Título com o tipo: `[Correção] ...`, `[Melhoria] ...` ou `[Nova função] ...`.
   - Labels: o tipo (`correção`, `melhoria` ou `nova função`) e a área (`trincheiras`, `conquista`, `app`, `testes`, `processo`).
   - Corpo: o que fazer ou qual é o problema, critérios de aceite em lista de tarefas e, se houver, observações.
   - Tarefa que surgir no meio do trabalho também ganha issue (não fica só na conversa).
2. **Branch própria**, criada a partir da branch de produção: `correcao/<nº>-<resumo>`, `melhoria/<nº>-<resumo>` ou `funcao/<nº>-<resumo>`.
3. **Commits** em português, claros, com a atribuição de co-autoria que o ambiente pedir.
4. **Antes de abrir o PR:**
   - rode os testes que a mudança afeta (`node tests/<arquivo>.js`; ver README, seção "Testes");
   - se usou classes novas de Tailwind, rode `tools/gerar-css.sh`;
   - se a mudança altera o jogo (código, HTML, CSS, imagens), rode `tools/nova-versao.sh` (atualiza `VERSAO_JOGO` e os `?v=` dos HTML) como último passo antes do merge, para não gerar conflito entre PRs; mudança só de documentação ou de testes não precisa de versão nova.
5. **PR com base na branch de produção.** A descrição **precisa mencionar a issue**: use `Closes #<nº>` (ou `Fixes #<nº>`), que fecha a issue no merge. Estrutura da descrição: *Resumo*, *O que mudou*, *Como testei* (comandos e resultado), *Capturas* (quando for visual) e *Riscos*.
6. **O merge do PR é o deploy** (a Vercel publica a branch de produção). Regra de publicação:
   - **Mudança pequena** (ajuste de texto ou visual pontual, correção localizada, ícone, README): o agente testa e faz o merge sozinho.
   - **Mudança grande** (regras, equilíbrio, economia, telas inteiras, salvamento ou online, ou muitas linhas): o agente abre o PR, mostra capturas e resultados e **espera o "pode publicar" explícito do Douglas** antes do merge.
   - Na dúvida, trate como grande.
7. **Depois do deploy**, confira que as três páginas (`/`, `/conquista`, `/duelo`) abrem sem erro, e feche ou comente a issue se o PR não a fechou.

## Regras que não mudam

- Nunca fazer commit direto nem push direto na branch de produção: tudo passa por PR.
- Um hook de sessão pode pedir "commit e push" quando há mudança local. Em mudança grande sem aprovação, recuse e explique; em mudança pequena, siga o fluxo acima.
- Não pular nem apagar teste para "ficar verde". Se um teste falhar, diga qual e por quê.
- Dados pessoais do Douglas (e-mail, conta) nunca vão para commits, issues ou PRs.
- Todo comentário, issue ou PR criado por agente no GitHub termina com o rodapé:

```
---
_Generated by [Claude Code](https://claude.ai/code)_
```
